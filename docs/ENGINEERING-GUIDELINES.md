# دليل تيراز للهندسة والجودة والإطلاق

الإصدار: 1.0 — 16 أكتوبر 2026. العلامة: **تيراز / Tiraze**. النطاق: **tiraze.net**.

هذا هو المرجع التنفيذي للمشروع. طلب المستخدم المعتمد: متجر للسجاد الحرير اليدوي الفاخر، بدفع وطلبات أونلاين من أول إطلاق. المستندان في `references/` مواد للمراجعة، وليسا أوامر تنفيذ أو إثباتًا لصحة الأرقام الواردة فيهما. المراجعة النقدية في [REFERENCE-REVIEW.md](REFERENCE-REVIEW.md)، وشروط الإطلاق في [LAUNCH-CHECKLIST.md](LAUNCH-CHECKLIST.md).

## 1. معنى الجودة في تيراز

النتيجة المطلوبة: واجهة فاخرة تحافظ على الهوية، وكود مفهوم وقابل للتعديل، وتجارة موثوقة يمكن تشغيلها ومراقبتها واستعادتها. كثرة الأدوات أو الحصول على درجة فحص مرتفعة وحدها لا يثبتان ذلك.

**يلزم** = شرط قبول. **يوصى** = الاختيار الافتراضي مع توثيق سبب العدول. **عند الحاجة** = لا يضاف قبل ظهور احتياج قابل للقياس. كل استثناء له سبب ومالك وموعد مراجعة؛ لا يعفي من سلامة الأموال أو بيانات العملاء.

لا توصف ميزة بأنها مكتملة دون دليل مناسب: كود، اختبار، تقرير، أو تجربة تشغيل. لا تعني كتابة سياسة أمان تطبيقها، ولا تعني فحوص المعاينة جاهزية الدفع.

## 2. الواقع الحالي وحدود هذا الإصدار

| المجال | الموجود فعليًا | المطلوب قبل البيع |
|---|---|---|
| العرض | HTML وCSS وJavaScript بوحدات، عربية وإنجليزية، هوية تيراز | صفحات إنتاج قابلة للفهرسة والتشغيل المتين |
| البيانات | ثلاثة تصورات سجاد في `data.js` | منتجات حقيقية وأسعار ومخزون ومواصفات وصور معتمدة |
| السلة | اختيارات في تخزين المتصفح | سلة ومعرّفات وأسعار تتحقق منها جهة التجارة |
| الطلب | موجز محلي قابل للتنزيل | طلب دائم برقم مرجعي وإشعارات وحالات وتتبّع |
| الدفع | غير متصل | تكامل معتمد، تحقق خلفي، تسويات واسترجاع |
| التشغيل | خادم Python للمعاينة | استضافة إنتاج ونسخ احتياطي ومراقبة وخطة تعافٍ |
| الاختبارات | فحوص عرض وتفاعل ومتصفح وفيديو | تكامل تجارة وأمان وحمل واستعادة وإتاحة |

`serve.py` ليس خادم إنتاج. تخزين بيانات التواصل محليًا في النسخة الحالية ليس التصميم النهائي للطلبات أو الحسابات. تقارير `qa/` أدلة للنطاق والتاريخ المدونين فقط. لا نعلن تحمل مليون طلب أو جاهزية أمنية بناء عليها.

## 3. قرارات البناء والتقنيات

### 3.1 القرار المعماري الافتراضي

يوصى بمحرك تجارة مُدار للمنتجات والمخزون والطلبات والدفع، مع واجهة تيراز المخصصة. يظل اختيار المزود معلقًا إلى أن تُثبت تغطيته لدولة الكيان والسوق والعملة والدفع والشحن والتكلفة والتصدير والنسخ الاحتياطي. راجع [ADR-0001](decisions/0001-commerce-launch-boundaries.md).

المرشح الأول للتقييم هو واجهة مخصصة فوق منصة تجارة مُدارة، مثل ثيم Shopify مخصص إذا نجح اختبار الملاءمة. يمكن بناء أقسام وقوالب بهوية تيراز داخل بنية الثيم؛ لا يلزم Headless لمجرد اختلاف التصميم. هذه توصية للتقييم، وليست اشتراكًا أو اعتمادًا نهائيًا. [معمارية ثيم Shopify](https://shopify.dev/docs/storefronts/themes/architecture)

| المسار | متى يناسب | أثره والتزاماته |
|---|---|---|
| ثيم مخصص + تجارة مُدارة | تحقيق التصميم والبلدان والتكاملات داخل المنصة | تشغيل أبسط؛ اختبار حدود التخصيص والتطبيقات والتكلفة |
| واجهة SSR/SSG مستقلة + تجارة مُدارة | مطلب مثبت لا يحققه الثيم أو قنوات متعددة | مسؤولية إضافية عن الجلسات والكاش وSEO والسلة والتحديثات |
| خلفية تجارة مخصصة معيارية | فجوة جوهرية مثبتة في المنصات المُدارة | ملكية دورة المال والمخزون والأمان والتشغيل كاملة |

لا تغيير إطار العمل أو إعادة بناء المشروع الآن لمجرد إعداد هذا الدليل. إذا لزم Headless، يُختار إطار واحد بعد نموذج يثبت العربية والفهرسة والسلة والدفع؛ لا يُفرض Next.js أو Nuxt أو غيرهما دون سبب. تستخدم الإصدارات المدعومة وقت التنفيذ، وتثبت نسخة أدوات البناء والحزم في المشروع.

لا نبدأ بخدمات مصغرة أو Kubernetes أو Kafka أو Sharding أو أربع طبقات كاش. الفصل المنطقي للميزات مطلوب؛ الفصل إلى خدمات يحتاج قياسًا يبرر عبء التشغيل. الميزانية والفريق وحجم الكتالوج وذروة الجلسات الفعلية مدخلات قرار التوسع.

### 3.2 مصدر الحقيقة

المنتج والسعر والخصم والعملة والمخزون والطلب تُدار في مصدر تجارة واحد. المتصفح يعرض ولا يقرر المبلغ المستحق أو حالة الدفع. محرك البحث والكاش وMerchant Center نُسخ مشتقة قابلة لإعادة البناء. لا توجد قاعدتا مخزون متنافستان.

## 4. الهيكل وجودة الكود

الهجرة تدريجية مع الحفاظ على الشكل والسلوك، وليست نقل ملفات تجميليًا. فصل مسؤوليات `app.js` وتوحيد CSS من أولويات البناء قبل تضخم المشروع.

```text
tiraze/
├── src/                         # عند الانتقال من المعاينة إلى مصدر منظم
│   ├── features/
│   │   ├── catalog/             # منتجات، فلاتر، مواصفات
│   │   ├── cart/                # سلة وحالة واجهة
│   │   ├── checkout/            # بدء الدفع وعرض النتائج
│   │   ├── orders/              # الطلبات والتتبع
│   │   └── search/
│   ├── shared/                  # مكونات وأدوات مستخدمة فعليًا
│   ├── i18n/                    # نصوص ولغات وصيغ
│   ├── styles/                  # tokens، أساس، مكونات، صفحات
│   └── seo/
├── integrations/                # حدود المنصة والدفع والشحن، إذا امتلكناها
├── tests/                       # unit، integration، e2e بحسب الحاجة
├── assets/                      # أصول الويب؛ الأصول الخام منفصلة
├── docs/                        # قرارات وأدلة تشغيل ومعايير
└── tools/                       # مهام قابلة لإعادة التشغيل
```

هذا مخطط حدود مسؤوليات، وليس إلزامًا بهيكل Monorepo. عند اعتماد ثيم، تبقى مجلدات المنصة القياسية هي الأعلى وتطبّق الحدود داخلها؛ لا نكسر بنية النشر لتقليد الشجرة.

- كود الميزات الجديدة المقسمة يستخدم TypeScript مع `strict` حيث تدعم سلسلة البناء ذلك؛ يمكن تثبيت عقود JavaScript الموروث بـJSDoc و`checkJs` أثناء الهجرة. لا إعادة كتابة شاملة من أجل الامتداد.
- تهيئة formatter وlint وفحص الأنواع وبناء قابل للتكرار وlockfile واحد عند إدخال مدير حزم. لا تثبيت حزم غير لازمة للمعاينة الحالية.
- فصل العرض عن الاتصال بالخدمات وقواعد التجارة. لا حساب أسعار حاسم داخل مكوّن UI.
- أسماء واضحة، ودوال ذات مسؤولية واحدة، وتجنب ملفات JS/CSS المصغرة يدويًا في المصدر. التصغير ناتج بناء فقط.
- تحقق عند حدود الثقة، وعالج الفشل برسالة مفيدة دون كشف تفاصيل داخلية. لا `catch` فارغًا يخفي فشل طلب أو دفع.
- لا تعديل `innerHTML` بمدخل عميل أو CMS غير موثوق دون ترميز بحسب السياق أو تنقية بمكتبة موثوقة عند الحاجة إلى HTML. ترميز النص وحده لا يؤمّن URL أو CSS.
- مراجعة أي اعتماد جديد: الحاجة، الترخيص، الصيانة، حجم الحزمة، الثغرات وبديل المنصة أو المكتبة الحالية.
- اختبارات تحمي السلوك والمخاطر، لا اختبارات تكرر التنفيذ. تقسيم تغييرات الهيكل عن تغييرات التصميم متى أمكن لتسهيل مراجعتها.
- كل PR يذكر السلوك الناتج والتحقق والمخاطر والترحيل وخطة الرجوع عند الحاجة. لا أسرار أو بيانات عملاء في الأمثلة أو fixtures أو لقطات الشاشة.

## 5. نموذج السجاد والكتالوج

السجاد قطعة فنية قد تكون فريدة؛ لا نعالجه كمنتج عام ذي مقاس مبهم.

| الكيان | الحد الأدنى من البيانات |
|---|---|
| منتج/قطعة | معرّف ثابت، SKU، slug، اسم ووصف عربي وإنجليزي، حالة نشر، مجموعة |
| مواصفات | خامات الوبر والسدى إن توفرت، أبعاد فعلية ووحدتها، اللون، بلد النسج، طريقة الصنع، الوزن للشحن |
| إثبات | مصدر المواصفات، جهة المراجعة وتاريخها، صور حقيقية للقطعة، العناية |
| عرض قابل للبيع | مبلغ دقيق وعملة، ضريبة وشحن محسوبان، مخزون أو مدة صنع مؤكدة |
| ميديا | الأصل وحقوقه وأبعاده ونصه البديل ومشتقاته؛ معرف مرتبط بالقطعة |

القطعة الفريدة يكون رصيدها الفعلي واحدًا متى كان ذلك واقعها. التصنيع حسب الطلب له سياسة تسعير ومدة وتخصيص مستقلة؛ لا زر شراء لمقاس غير مسعّر. لا ننسب صورًا مولّدة إلى مخزون حقيقي أو نخترع كثافة عقد أو منشأ أو شهادة أو تقييمًا أو GTIN. لا نضيف معرفًا غير موجود لملء JSON-LD.

الطلب يحتفظ بلقطة تاريخية للسعر والعملة والضرائب والمنتج والعنوان وقت اعتماده؛ تعديل الكتالوج لاحقًا لا يغيّر الفاتورة القديمة. الأموال أعداد صحيحة بالوحدة الصغرى المناسبة للعملة أو أرقام عشرية دقيقة، مع قواعد تقريب موثقة؛ لا افتراض أن كل العملات لها منزلتان ولا استخدام floating point دون ضبط للمحاسبة.

## 6. السلة والطلب والدفع

### 6.1 تجربة الشراء

الشراء كزائر متاح حيث تسمح المنصة والمتطلبات الفعلية. التكلفة الإجمالية والعملة والشحن والضريبة ومدة التنفيذ وسياسة الإرجاع واضحة قبل التأكيد. تغيير البلد يعيد تسعير السلة؛ لا يُستنتج البلد أو العملة من لغة الواجهة وحدها.

الحقول لها تسميات وأخطاء محددة مع حفظ المدخلات الآمن عند الفشل. لا نفرض عددًا عالميًا للحقول؛ نجمع ما يحتاجه الشحن والتحقق فعلًا. إيصال الطلب يظهر فقط بعد الحصول على مرجع دائم، مع التمييز بين انتظار الدفع ونجاحه.

### 6.2 دورة الحياة

حالة الطلب وحالة الدفع وحالة التنفيذ مستقلة. قد يكون الطلب مؤكدًا تجاريًا والدفع معلقًا بحسب وسيلة الدفع؛ لا يُساوى إرسال طرد بنجاح تحصيل المال.

```text
طلب: مسودة → بانتظار التأكيد/الدفع → مؤكد → مغلق أو ملغى
دفع: pending → authorized أو succeeded أو failed أو canceled
استرجاع: none → pending → partial/refunded أو failed
تنفيذ: unfulfilled → preparing → shipped → delivered أو returned
```

هذا نموذج مفاهيمي؛ تُربط الحالات بأسماء مزود التجارة الفعلية دون اختراع سير متعارض معه. الاسترجاع الجزئي والفشل والاعتراض المالي حالات يجب تصميمها.

- إنشاء الطلب/محاولة الدفع بمفتاح idempotency مستقر لمحاولة العميل، لا مفتاح جديد لكل إعادة إرسال. مفتاح واحد مع payload مختلف يُرفض أو يعالج وفق العقد.
- لا يؤكد success URL أو screenshot أو قيم المتصفح دفعًا. التحقق خلفي عبر المزود والحدث الموثّق أو استعلام خادمي موثوق.
- webhook: تحقق التوقيع وفق طريقة المزود على raw body عند اشتراطها، وبيئة الحساب، ومنع إعادة المعالجة. يتم تثبيت الاستلام في تخزين دائم قبل الرد بالنجاح؛ العمل الطويل خارج الطلب.
- الأحداث قد تتكرر أو تصل خارج الترتيب. سجل دائم للحدث والمعاملة، وانتقالات حالة مسموحة، ومطابقة لاحقة مع المزود. أمثلة هذه المخاطر موثقة رسميًا لدى [Stripe](https://docs.stripe.com/webhooks)؛ المرجع لا يعني اختيار Stripe لتيراز.
- انقطاع الاتصال بعد طلب التحصيل ينتج حالة «غير محسومة» إلى أن تتم المطابقة. لا تحاول تحصيل المبلغ تلقائيًا لدى بوابة ثانية قبل حسم الأولى.
- الإشعارات والفواتير والشحن لا تُنشأ مرتين عند تكرار الحدث. إذا امتلكنا التكامل، يُستخدم سجل أحداث دائم/outbox أو بديل مكافئ تديره المنصة.
- تقرير تسوية دوري يربط الطلبات والتحصيل والرسوم والاسترجاع والتحويل البنكي، مع صف للحالات غير المطابقة ومالك لمعالجتها. لا مساواة بين إجمالي المبيعات ورصيد البنك.

## 7. المخزون والاتساق

الإضافة للسلة ليست بيعًا ولا حجزًا بالضرورة. يحدد العقد متى يبدأ الحجز ومدة صلاحيته حسب وسيلة الدفع؛ المهلة ليست خمس دقائق ثابتة لجميع الحالات.

- عند امتلاك مخزون مخصص: حجز دائم داخل معاملة وتحديث شرطي أو قفل مناسب، مع عدم السماح برصيد سالب، وربط الحجز بالطلب/المحاولة.
- تأكيد الحجز أو تحريره يحدث مرة واحدة. عامل انتهاء قابل لإعادة التشغيل ومطابقة دورية يعيدان الحجوزات المنتهية، مع سياسة للدفع الذي يصل بعد انتهاء الحجز.
- لا Redis بوصفه المصدر الوحيد لمخزون مالي حساس. انتهاء مفتاح TTL لا يعيد عدادًا آخر تلقائيًا؛ إشعارات Redis ليست سجلًا دائمًا، وقد تتأخر أو تضيع عند الانقطاع. [توثيق Redis](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/)
- إذا كانت المنصة تدير المخزون، نعتمد آلياتها ونختبرها بدل إنشاء حجز منافس في Redis.
- معيار قبول حاسم: محاولات متزامنة لآخر سجادة لا تنتج أكثر من تخصيص نهائي واحد؛ نتيجة الدفع المتأخر لها معالجة تعويضية واضحة ولا تتحول إلى بيع وهمي.

## 8. الأمان والخصوصية

تحدد مصفوفة أمان تستند إلى [OWASP ASVS](https://owasp.org/projects/asvs) مع تثبيت الإصدار والضوابط المنطبقة والدليل والمالك. ASVS مرجع تحقق، وليس شهادة حصلنا عليها بمجرد ذكره.

- HTTPS في الإنتاج؛ أسرار في مخزن أسرار/إعدادات خادمية، مفاتيح منفصلة للبيئات، أقل صلاحية وتدوير وإلغاء موثق. لا مفتاح سري في frontend أو Git أو logs أو ملفات التنزيل.
- لا تخزين PAN أو CVV، ولا المرور ببيانات البطاقة الخام في خوادمنا؛ استخدام checkout/حقول مُدارة وفق المزود. اختيار الاستضافة أو iframe يقلل نطاق المسؤولية ولا يلغيها.
- نطاق PCI DSS والتقييم المطلوب يراجعان مع مزود الدفع/الجهة المختصة. مراقبة سكربتات الدفع ومتطلبات 6.4.3 و11.6.1 تُحدد حسب طريقة الدمج؛ لا نعتمد ترقيمًا من نموذج قديم. [PCI SSC](https://blog.pcisecuritystandards.org/coffee-with-the-council-podcast-guidance-for-pci-dss-e-commerce-requirements-effective-after-31-march-2025)
- كل قراءة/تعديل طلب أو عنوان أو فاتورة يتحقق من الهوية والملكية والدور خادميًا؛ UUID ليس تفويضًا. حسابات الإدارة لها MFA وصلاحيات محدودة وسجل تدقيق.
- الحقول المسموحة محددة؛ السعر والخصم والرصيد وحالة الدفع لا تُقبل من العميل بوصفها حقائق. استعلامات SQL ممررة بمعاملات، وتحميل الملفات يقيّد النوع والحجم ويُفحص عند وجوده.
- جلسات خادمية أو آلية المنصة المعتمدة؛ cookies الحساسة `Secure` و`HttpOnly` و`SameSite` المناسب لتدفق الدفع. حماية CSRF حيث تنطبق؛ استثناء webhook لا يعفيه من التوقيع. CORS بقائمة أصول مقصودة، وليس بديلًا للتفويض.
- rate limits مدروسة لمسارات تسجيل الدخول والاسترداد والبحث والكوبونات والدفع، ورسائل لا تكشف وجود حساب، مع تدهور مفهوم بدل إغلاق المتجر على المستخدم الحقيقي.
- CSP مبنية على جرد النطاقات والسكربتات الفعلية وتُختبر أولًا؛ لا نسخ nonce شكلي أو فرض Trusted Types يكسر الموقع. `nosniff` وسياسة referrer وقيود framing وصلاحيات المتصفح تُختبر مع checkout.
- HSTS يفعّل تدريجيًا بعد جاهزية HTTPS؛ `includeSubDomains` وpreload قرارات مستقلة بعد حصر النطاقات، وليسا سطرًا إلزاميًا ينسخ عشوائيًا. [MDN HSTS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security)
- بيانات العملاء بالحد اللازم، مدد احتفاظ وحذف/تصحيح وتصدير وصلاحيات وصول، ونسخ احتياطية مشفرة. لا تخزين بيانات الاتصال طويلًا في localStorage كتصميم إنتاج. حسابات التحليلات والتسجيل تحجب PII ومعرّفات الجلسات الحساسة.
- شروط الخصوصية والفاتورة والضريبة والاسترجاع والتجارة العابرة للحدود تعتمد وفق دولة الكيان والأسواق؛ لا أسعار ضرائب أو وسائل دفع أو مدد إلزامية مفترضة من المستندين.

## 9. الأداء والميديا والكاش

### 9.1 قياس فعلي وحدود مبدئية

أهداف Core Web Vitals: **LCP ≤ 2.5s، INP ≤ 200ms، CLS ≤ 0.1 عند p75** مع فصل الموبايل والكمبيوتر. الاختبارات المعملية قبل الإطلاق لا تثبت INP الميداني أو اجتياز الزوار الفعليين. [web.dev](https://web.dev/articles/vitals)

هذه ميزانيات داخلية أولية للمراجعة على جهاز متوسط وشبكة مقيدة، وليست معايير عالمية أو نتائج حققناها:

| العنصر | الميزانية المبدئية | دليل المراجعة |
|---|---|---|
| JavaScript أولي مملوك للمشروع | ≤ 150 KiB مضغوط | تقرير build يفصل سكربتات الطرف الثالث |
| CSS أولي | ≤ 75 KiB مضغوط | أحجام بعد البناء وحذف غير المستخدم |
| صورة افتتاحية للموبايل | ≤ 250 KiB متى حافظت على التفاصيل | الصورة الفعلية وقياس LCP، لا امتداد الملف فقط |
| فيديو الموبايل | نسخة مستقلة تستهدف ≤ 2 MiB للدورة | قياس الحجم والجودة وبدء التشغيل؛ أي تجاوز له دليل وسبب |
| هدف توافر مبدئي | 99.9% شهريًا للرحلات المملوكة | قياس خارجي؛ فصل أخطاء المزود عن أخطاء المتجر في التقرير |
| API مملوكة غير شاملة زمن المزود | p95 ≤ 500ms تحت حمل موثق | سيناريو وبيئة وتزامن وأخطاء واضحة |

### 9.2 الصور والفيديو

الـHero **فيديو** من قرارات تجربة تيراز. يُحافظ عليه مع `muted` و`loop` و`playsinline` وإيقاف/تشغيل وصورة poster خفيفة. عند تقليل الحركة يبدأ ثابتًا؛ عند فشل التشغيل تبقى الصورة والنص والروابط قابلة للاستخدام. لا استبدال دائم للفيديو بصورة لتسهيل التنفيذ. يمكن تأجيل جلب الفيديو أو اختيار نسخة أخف حسب سياسة الشبكة/البيانات المدعومة والمختبرة.

الصور الرئيسية ليست lazy؛ ما دون الشاشة يؤجل. أبعاد أو `aspect-ratio` تمنع القفز، و`srcset/sizes` تناسب العرض. نقارن AVIF/WebP/JPEG بالجودة والحجم وسرعة الفك على الأجهزة المستهدفة؛ لا ضمان ضغط بنسبة ثابتة أو DPR موحد لكل صورة. التكبير على صفحة سجادة له مصدر أدق يُطلب عند الحاجة. يحتفظ الأصل وحقوقه بعيدًا عن مسار تحميل الزائر، ولا يُنشر فيديو الخام أو صورة ضخمة بسبب سهولة نسخها.

شعار تيراز الحالي raster شفاف؛ master متجهي مضبوط مطلوب عند تسليم الهوية نهائيًا، ولا توصف صورة PNG بأنها SVG. الخطوط محددة الأوزان واللغات مع fallback وحمل محدود.

### 9.3 سياسة الكاش

| البيانات | السياسة |
|---|---|
| ملفات ذات بصمة محتوى | `public` مع مدة طويلة و`immutable` بعد اعتماد التسمية |
| HTML وكتالوج عام | TTL وإبطال موثقان ومتوافقان مع المنصة؛ لا وعد بمخزون قديم |
| سلة/checkout/حساب/طلب شخصي | استبعاد من الكاش المشترك؛ `private, no-store` للاستجابات الحساسة التي نملكها |
| سعر وتوفر قبل الدفع | إعادة تحقق سلطوية في محرك التجارة مهما كانت نتيجة الكاش |

المفتاح يراعي اللغة والسوق والعملة والحقول التي تغيّر المحتوى. يجب اختبار تسريب جلسة أ إلى ب وسيناريو تغيير سعر أو نفاد قطعة. لا نفترض أن مجرد إضافة `Vary` أو منع التخزين يصلح كل الطبقات السابقة. [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

## 10. العربية والإتاحة وتجربة الفخامة

الاسم العربي **تيراز**، الإنجليزي **Tiraze**، الشعار والعاجي والكحلي والذهبي كما اعتمدت. لا يغيّر تحسين تقني الهوية أو شكل الخط أو تجربة الهيرو دون سبب واضح ومراجعة ناتجه.

- Mobile-first مع اختبار 320 و390 و768 و1024 و1440 بكسل، أفقي/رأسي وتكبير 200%؛ لا يقتصر التابلت على نسخة هاتف ممدودة.
- CSS منطقي (`margin-inline` ونحوه)، واتجاه RTL/LTR متعمد. الأرقام وSKU والعملات والعناوين المختلطة تختبر؛ لا قلب صور المنتجات آليًا مع اتجاه اللغة.
- هدف WCAG 2.2 AA مع تدقيق يدوي ولوحة مفاتيح وقارئ شاشة، وليس ادعاء توافق من فحص آلي. حد النص العادي 4.5:1 والكبير 3:1؛ متطلبات تباين عناصر الواجهة تختلف عن النص والشعار. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- قاعدة المشروع 44×44 CSS px للأزرار المهمة باللمس. معيار Target Size AA له حد 24×24 واستثناءات للمسافة وغيرها؛ لا نحذف الاستثناءات عند نسب الكلام إلى المعيار. [شرح W3C](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)
- focus ظاهر وغير محجوب، وأسماء مفهومة للأيقونات، وdialog بإدارة تركيز صحيحة وإغلاق واضح. رسائل أخطاء الحقول مرتبطة بها والتغييرات المهمة معلنة لقارئ الشاشة.
- الذهب للزينة والنصوص التي تجتاز التباين فقط، لا للنص الصغير على العاجي تلقائيًا. لا معلومة محصورة في اللون أو الحركة.
- تقليل الحركة يُحترم، والمعرض قابل للتحكم. لا أنماط ضغط مزيفة أو ندرة أو تقييمات مصطنعة.

## 11. SEO وتعدد الأسواق

صفحات المنتجات والمجموعات الأساسية تقدم HTML ومعلومات وmetadata قابلة للفهرسة عبر توليد خادمي/ثابت أو المنصة المختارة. مجرد تغيير `document.title` بعد تشغيل JavaScript ليس خطة SEO كاملة.

- URL ثابت، وcanonical صحيح، وحالات HTTP فعلية 404/redirect للروابط المنتهية. لا fallback يعيد 200 لكل slug غير موجود في الإنتاج.
- بنية اللغة/السوق تُحسم مرة وتوثّق خريطة تحويل للقديم. `hreflang` فقط لنسخ منشورة فعلًا وبروابط متبادلة. لا إنشاء صفحات دولة وهمية أو تحويل إجباري بالـIP. [دليل Google للروابط](https://developers.google.com/search/docs/specialty/ecommerce/designing-a-url-structure-for-ecommerce-sites)
- title وdescription وOpen Graph ملائمة للصفحة؛ بيانات Product/Offer تطابق السعر والعملة والتوفر والنص المرئي وخلاصة المنتجات. لا GTIN أو مراجعات مخترعة.
- sitemap للروابط الأساسية المنشورة، وسياسة للفلاتر وتكرار المتغيرات. `noindex` يحتاج أن يستطيع الزاحف قراءة الصفحة؛ `robots.txt` ليس حاجز خصوصية ولا بديلًا دائمًا للتحكم بالفهرسة.
- preview/staging محمية من الوصول العام غير المقصود، ومع `noindex` كطبقة إضافية؛ الإنتاج يُراجع كي لا يرث الحظر.
- `llms.txt` تجربة اختيارية إذا وجدت فائدة قابلة للقياس، وليس شرط إطلاق أو ضمان ظهور. Google لا يطلب ملف AI خاصًا للظهور في ميزاته. [Google AI features](https://developers.google.com/search/docs/appearance/ai-features)

## 12. الاختبارات وCI وإدارة الإصدارات

مسار CI مستهدف: تثبيت ثابت → formatting/lint → أنواع → unit للمنطق الحاسم → integration → build → E2E أساسية → فحص أسرار واعتمادات → artifact موثق. يرتبط كل تقرير بالـcommit والبيئة؛ نجاح محلي قديم لا يغطي تغييرًا لاحقًا.

اختبارات التجارة الإلزامية قبل الإطلاق: إعادة إرسال الطلب؛ حدث دفع مكرر/متأخر/بتوقيع خاطئ؛ انقطاع بعد التحصيل؛ تغيير السعر قبل الدفع؛ شراء آخر قطعة بالتزامن؛ استرجاع جزئي؛ فشل الشحن/البريد؛ منع عميل من قراءة طلب آخر؛ خروج عملة/ضريبة خاطئة؛ بدء جلسة/سلة من جهاز جديد وفق سياسة المنصة.

E2E على Chromium وFirefox وWebKit عند تجهيز CI، ومع أجهزة Safari iOS وChrome Android فعلية قبل الإطلاق. تشمل زيارة مباشرة/refresh، بحث وتصفية، منتج ومقاس، سلة، checkout، تأكيد/فشل، عربية وإنجليزية، لوحة مفاتيح وفيديو وتقليل حركة. لا تكفي mocks أو screenshots لتأكيد سلوك دفع حقيقي.

التغييرات المرئية المهمة ترفق بصورة للكمبيوتر والموبايل. اختبارات الدفع على sandbox؛ تجارب مالية حقيقية محدودة فقط ضمن خطة تشغيل معتمدة ومطابقة مالية. لا اختبارات حمل على مزود خارجي بلا نطاق مسموح.

## 13. الاستقرار والتشغيل والتعافي

- بيئات local وstaging وproduction منفصلة بحسابات ومفاتيح وبيانات. staging لا يرسل رسائل حقيقية عشوائيًا ولا يشارك قاعدة بيانات الإنتاج.
- المهام غير المتزامنة لها retry محدود مع backoff/jitter وdead-letter أو قائمة أخطاء مكافئة، ومالك لإعادة المعالجة. retries لا تعني تكرار خصم أو استرجاع أو شحنة.
- deadlines وtimeouts لكل اتصال خارجي، ورقم تتبع آمن لكل عملية. عند انقطاع الدفع يظل التصفح متاحًا وتظهر حالة واضحة بدل نجاح زائف.
- مراقبة أخطاء الواجهة والخادم وبدء/نجاح الدفع وأحداث webhook المتراكمة والحجوزات والاسترجاعات غير المحسومة. تنبيهات قابلة للتصرف موجهة لمسؤول فعلي، دون PII في logs.
- خطة حمل تحدد التزامن والجلسات في الثانية وحجم الكتالوج ونسبة الطلبات إلى التصفح؛ الحمل المتدرج والذروة والاستمرار يسبق ادعاء السعة. لا «ملايين» دون سيناريو ونتيجة.
- أهداف أولية للتخزين الذي نملكه: RPO ≤ 15 دقيقة، RTO ≤ 4 ساعات، تُراجع مع القدرة والتكلفة. المنصة المُدارة تحتاج دليل قدراتها وخطة تصدير/استعادة مناسبة؛ لا نفترض نسخة backup شاملة من API وحده.
- تمرين restore قبل الإطلاق ودوريًا بعده، مع سجل زمن وبيانات استعيدت وعمليات مطابقة مالية. وجود ملف backup ليس دليل نجاح الاستعادة.
- نشر artifact قابل للتعقب، migrations قابلة للتدرج، rollback مجرب. الرجوع للواجهة لا يلغي أحداث دفع تمت أثناء الإصدار؛ استعادة بيانات مالية تتطلب مطابقة مستقلة.

## 14. خارطة التحويل من المعاينة إلى متجر

| المرحلة | المخرجات | بوابة الخروج |
|---|---|---|
| أ: تعريف تجاري | دولة الكيان والأسواق والعملات والمنتجات والشحن والميزانية | سجل قرارات مكتمل وأصحاب مسؤولية |
| ب: إثبات منصة | قطعة حقيقية بمخزون 1، checkout تجريبي، webhook واسترجاع وشحن | اختبار تقني/تشغيلي يثبت ملاءمة المزود |
| ج: بناء منظم | مصدر مقسم وdesign tokens وصفحات لغتين وكتالوج حقيقي وSEO | CI وعرض مطابق وتجربة شراء مترابطة |
| د: حماية وتشغيل | تحقق أمني ومراقبة وbackup واستعادة وحمل وسياسات فعلية | إغلاق جميع شروط الإطلاق الحرجة بدليل |
| هـ: إطلاق | نطاق وHTTPS وكتالوج وأسعار ووسائل دفع معتمدة | smoke test ومتابعة ومطابقة بعد النشر |

المتجر الكامل شرط الإطلاق؛ ليس معنى ذلك اختراع تكامل دفع اليوم دون اختيار السوق والمزود والكيان. المهمة الحالية تضع دليل التنفيذ وتغيّر الاسم، ولا تدّعي إنجاز البنية الخلفية.

## 15. إدارة الدليل

تُراجع الروابط والإصدارات عند اختيار المزود وقبل الإطلاق، وعند تغيير عقد الدفع أو الاستضافة. القرارات الغالية الرجوع لها تُوثّق في `docs/decisions/`. الأصلان محفوظان للمقارنة، وأي تعارض يُحل وفق قرار المشروع الموثق وطلب المستخدم الحالي. مصدر الأرقام الداخلية هو قرار قياس للمشروع، لا نسبة مزعومة إلى معيار خارجي.
